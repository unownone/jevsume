# PDF.js preview and annotation research

Research target: `pdfjs-dist` 6.3.289, the version declared by jevsume. PDF.js separates its core parser, display API, and full viewer UI; a custom React preview should use the display API rather than embed the default viewer chrome. ([PDF.js getting started](https://mozilla.github.io/pdf.js/getting_started/), [pdfjs-dist 6.3.289](https://www.npmjs.com/package/pdfjs-dist))

## Page rendering to canvas

Load bytes with `getDocument({ data })`, await `loadingTask.promise`, and retrieve pages with the one-based `pdf.getPage(pageNumber)` API. `PDFPageProxy.getViewport({ scale })` returns the dimensions and transform required for rendering, and `page.render({ canvas, viewport })` returns a `RenderTask` whose `promise` resolves when rendering finishes. In 6.3, passing `canvas` is preferred; `canvasContext` remains for backward compatibility. ([PDF.js examples](https://mozilla.github.io/pdf.js/examples/), [PDFPageProxy API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html), [6.3.289 API source](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/api.js))

For sharp HiDPI output, give the canvas backing store `viewport.width * devicePixelRatio` by `viewport.height * devicePixelRatio`, keep its CSS size at `viewport.width` by `viewport.height`, and pass `[outputScale, 0, 0, outputScale, 0, 0]` as the render transform. PDF.js’s official example uses this exact split between backing pixels and CSS pixels. ([PDF.js examples](https://mozilla.github.io/pdf.js/examples/))

The same canvas must not be used for simultaneous page renders. React cleanup should retain the returned `RenderTask`, call `cancel()` when a render is superseded or the component unmounts, and await or handle its promise before starting another render on that canvas. ([PDF.js examples](https://mozilla.github.io/pdf.js/examples/), [6.3.289 `RenderTask` source](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/api.js))

## Worker configuration

`GlobalWorkerOptions.workerSrc` must be a string containing the path and filename of the worker, and PDF.js says it should always be set. The existing Vite setup already imports `pdfjs-dist/build/pdf.worker.min.mjs?url` and assigns that emitted URL before `getDocument`, which is the correct shape for the 6.3 API. ([6.3.289 worker options](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/worker_options.js), [official component example](https://github.com/mozilla/pdf.js/blob/v6.3.289/examples/components/pageviewer.mjs), [local extraction module](file:///workspace/src/lib/extract.ts))

Keep the worker and display code on the same installed `pdfjs-dist` version by importing both from the package build. Do not assign an imported worker module object to `workerSrc`; PDF.js validates that the value is a string URL/path. ([6.3.289 worker options](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/worker_options.js), [PDF.js worker validation change](https://github.com/mozilla/pdf.js/pull/17504))

## Text content and text layer

`page.getTextContent()` resolves to a `TextContent` object with `items`, `styles`, and `lang`; each `TextItem` contains `str`, direction, a transform matrix, width, height, font name, and end-of-line flag. PDF.js normalizes whitespace occurrences to ordinary spaces, so concatenating `str` values is useful for extraction but is not a lossless character-offset model by itself. ([PDF.js module API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html), [PDFPageProxy API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html))

For selectable/copyable text over the canvas, PDF.js 6.3 exposes `TextLayer`. Construct it with `textContentSource` from `page.streamTextContent()` or `getTextContent()`, the page viewport, and an absolutely positioned container, then await `textLayer.render()`. The class creates positioned transparent text spans and supports `update({ viewport })` for scale or rotation changes. ([6.3.289 `TextLayer` source](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/text_layer.js), [6.3.289 text-layer CSS](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/text_layer_builder.css))

Use the matching PDF.js text-layer CSS behavior (absolute container, transparent spans, `transform-origin: 0 0`, selection enabled) or copy only the required rules into jevsume’s styles. A `TextLayer` without those layout rules is not a complete visual layer. ([6.3.289 text-layer CSS](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/text_layer_builder.css), [6.3.289 `TextLayerBuilder`](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/text_layer_builder.js))

Jevsume currently calls `getTextContent()` and joins item strings with spaces. Preserve that extraction path for Jev input, but run a separate per-page text-content/mapping path for preview anchoring because overlay regions need page identity and geometry rather than only the flattened string. ([PDF.js `TextItem` API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html), [local extraction module](file:///workspace/src/lib/extract.ts))

## Coordinates and zoom

`PageViewport` accounts for page user units, scale, rotation, offsets, and the PDF-to-canvas Y-axis flip. Store custom annotation geometry in unscaled PDF page coordinates, then convert it for the current viewport; convert pointer coordinates back with `viewport.convertToPdfPoint(x, y)`. This lets desktop and mobile use the same persisted model while deriving CSS positions at each zoom. ([6.3.289 `PageViewport` source](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/page_viewport.js))

Important version correction: `convertToViewportRectangle` does **not** exist in `pdfjs-dist` 6.3.289. It was removed before 6.1 as unused; PDF.js’s migration note says to replace it with two `convertToViewportPoint` calls. Convert both rectangle corners, then normalize the resulting X and Y pairs with `Math.min`/`Math.max` so rotations and the Y flip cannot produce a negative CSS width or height. ([removal PR and migration example](https://github.com/mozilla/pdf.js/pull/21426), [6.3.289 `PageViewport` source](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/page_viewport.js), [6.3.289 type definition](https://app.unpkg.com/pdfjs-dist@6.3.289/files/types/src/display/page_viewport.d.ts))

For committed zoom changes, create a new viewport at the new scale, resize and rerender the canvas, and update/recreate the text and overlay layers from that same viewport. PDF.js’s example derives a scale from the desired CSS width, while `TextLayer.update` and `AnnotationLayer.update` accept an updated viewport. ([PDF.js examples](https://mozilla.github.io/pdf.js/examples/), [6.3.289 `TextLayer` source](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/text_layer.js), [6.3.289 `AnnotationLayer` source](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/annotation_layer.js))

## PDF.js annotation layer versus a jevsume SVG overlay

PDF.js’s `AnnotationLayer` is for annotations already represented by the PDF display API, including links, widgets, popups, and other PDF annotation types. The viewer builder obtains them with `page.getAnnotations({ intent: "display" })`, constructs `AnnotationLayer` with a viewport cloned using `dontFlip: true`, and renders into an absolutely positioned DOM layer. ([PDFPageProxy API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html), [6.3.289 `AnnotationLayerBuilder`](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/annotation_layer_builder.js), [6.3.289 annotation CSS](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/annotation_layer_builder.css))

That layer is not the right ownership boundary for jevsume review boxes, pins, chat anchors, or triggers. Those objects are application state, so render them in a separate SVG (or DOM) overlay sharing the canvas’s CSS width, height, viewport, and page wrapper. Keep PDF.js’s annotation layer only when jevsume needs native PDF links/forms/existing annotations; place the custom overlay as its own sibling layer with an explicit z-order and pointer-event policy. This recommendation follows the distinct responsibilities exposed by PDF.js’s annotation and text-layer APIs. ([6.3.289 `AnnotationLayerBuilder`](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/annotation_layer_builder.js), [6.3.289 `TextLayerBuilder`](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/text_layer_builder.js), [PDF.js layer overview](https://mozilla.github.io/pdf.js/getting_started/))

The page wrapper should therefore stack, from back to front: rendered canvas, optional transparent text layer, optional native PDF annotation layer, and jevsume’s SVG review layer. Adjust pointer events by mode so text selection, native links/forms, and custom handles do not all compete for the same gesture. PDF.js’s own CSS uses absolute layers and controls pointer events at the annotation-section level, which is the first-party pattern to preserve. ([6.3.289 text-layer CSS](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/text_layer_builder.css), [6.3.289 annotation-layer CSS](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/annotation_layer_builder.css))

## Do not mutate PDF annotation dictionaries for this feature

Jevsume should not write review state into PDF annotation dictionaries. PDF.js maintainers state that `AnnotationStorage` uses a custom PDF.js format, cannot accept copied `getAnnotations()` data, and manually inserted entries are not automatically rendered; historically, programmatic creation has also supported only selected editor annotation types rather than arbitrary PDF annotations. ([Mozilla issue on programmatic annotation creation](https://github.com/mozilla/pdf.js/issues/16168), [Mozilla issue on editing existing annotations](https://github.com/mozilla/pdf.js/issues/15403))

Although `PDFDocumentProxy.saveDocument()` can serialize supported changes from `annotationStorage`, its API warns when storage is empty and directs callers wanting the original bytes to `getData()`. That persistence path is unnecessary for boxes, pins, threads, and triggers that belong in jevsume’s own data model and need not alter the uploaded resume. ([6.3.289 API source](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/api.js), [PDF.js annotation-storage API change](https://github.com/mozilla/pdf.js/pull/13207))

## Recommendation for jevsume

1. Keep `pdfjs-dist` 6.3.289 and the current Vite worker URL configuration; use the display API directly, not the full viewer chrome. ([pdfjs-dist package](https://www.npmjs.com/package/pdfjs-dist), [PDF.js layer overview](https://mozilla.github.io/pdf.js/getting_started/))
2. Build one page wrapper per visible page with a HiDPI canvas and a single shared `PageViewport` for every layer. ([PDF.js examples](https://mozilla.github.io/pdf.js/examples/), [6.3.289 `PageViewport`](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/page_viewport.js))
3. Add `TextLayer` only where selection/accessibility or text anchoring requires it; retain structured `TextItem` geometry separately from the flattened Jev extraction string. ([6.3.289 `TextLayer`](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/text_layer.js), [PDF.js `TextItem` API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html))
4. Store jevsume boxes and pins in unscaled PDF page space and draw a custom SVG overlay; in 6.3 convert rectangle corners with two `convertToViewportPoint` calls because `convertToViewportRectangle` has been removed. ([6.3.289 `PageViewport`](https://github.com/mozilla/pdf.js/blob/v6.3.289/src/display/page_viewport.js), [removal PR](https://github.com/mozilla/pdf.js/pull/21426))
5. Treat PDF.js `AnnotationLayer` as optional compatibility for annotations already in the PDF, and keep jevsume review/chat/trigger state outside the PDF rather than mutating annotation dictionaries. ([6.3.289 `AnnotationLayerBuilder`](https://github.com/mozilla/pdf.js/blob/v6.3.289/web/annotation_layer_builder.js), [Mozilla annotation-storage guidance](https://github.com/mozilla/pdf.js/issues/16168))

## Remaining uncertainty

The exact correspondence between Jev’s flattened character offsets and PDF.js `TextItem` strings is document-dependent because PDF.js normalizes whitespace and emits text in items rather than guaranteeing a single source-text stream. The span-to-glyph research task should define matching, fallback, and confidence behavior before production anchoring is implemented. ([PDFPageProxy `getTextContent` note](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html), [PDF.js `TextContent` and `TextItem` API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html))
